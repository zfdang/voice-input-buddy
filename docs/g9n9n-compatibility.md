# G9N9N 语音支持与按键映射限制

更新日期：2026-10-28。适用产品：Voice Input Buddy 的 macOS 版本。

## 当前支持范围

**G9N9N 的语音功能部分支持，普通单键映射不支持；另有实验性的双键 Enter 功能。** 实测样机的语音键和麦克风可用，但普通单键及松开报告的长度与设备自己的 HID 描述符不一致。macOS 没有将这些短报告交给应用，因此方向、确定、返回等按键不能作为可靠的控制输入。

这一产品支持范围依据下述 A0、固件 26.7 样机的实测制定。它不代表每一支 G9N9N 或所有兼容款都具有同一固件问题；其他样机必须分别通过单键、松开和持续按住测试，才能扩大其受支持功能。

| 功能 | 当前状态 | 使用边界 |
| --- | --- | --- |
| 蓝牙连接与 ATVV 能力协商 | 已实测可用 | 仍须通过设备身份和音频能力检查 |
| 语音键与遥控器麦克风 | 已实测可用 | 使用独立 ATVV 蓝牙服务；用户已确认语音输入工作 |
| 音频解码及虚拟麦克风输出 | 已实测可用 | 16 kHz IMA ADPCM，送入 Voice Input Buddy Mic；目标输入工具仍须实际验证 |
| 语音键触发输入工具快捷键 | 已实测可用 | 与普通按键的自定义映射是两条不同路径 |
| 普通按键映射 | **不支持** | 单键和松开事件无法可靠到达应用；不能据此提供方向、确认、返回、主页、音量等控制映射 |
| OK＋任意方向键 | 实验性 Enter，尚待真机验收 | 需开启自定义按键映射并由应用独占设备；每份完整组合报告发送一次 Enter。无法收到松开报告，若设备重复发送报告可能重复输入；不支持长按或按住连发 |
| 普通按键长按和连发 | **不支持** | 缺少完整按下／松开状态 |
| 完整首次配置、长会话、休眠与重连 | 尚未完成整体验收 | 向导中的普通按键检查可通过下述双键方法继续；其他步骤和生命周期仍须分别验证 |

语音输入工具的按住或点按触发设置仍按该工具的实际配置验证。本文不把音质、所有工具的开始／停止行为或全部会话场景概括为已经通过。

## 设置时如何完成按键检查

G9N9N 可以利用双键产生的完整报告完成向导中的按键检查，然后继续配置语音功能。向导会显示 G9N9N 专用提示；操作如下：

1. **最初的 OK 键验证**：同时按下 OK（确定）和上方向键，检测到输入后全部松开；此时不要按语音键。
2. **后续普通按键测试**：先同时按 OK＋上，全部松开，再同时按返回＋上，最后全部松开。这样能累计检测到 OK、上、返回三个不同按键，满足原有的检查条件。
3. 继续完成麦克风驱动、输入工具和语音测试。双键提示不跳过权限检查、音频检查或实际语音验证。

**这里通过的是设置阶段的按键报告检查，不是普通按键映射功能验收。** 设置完成后，语音键和麦克风可以工作，普通单键映射及松开行为仍不受支持。实验性 Enter 组合的条件与限制见下文。

## 测试环境与问题表现

| 项目 | 实测值 |
| --- | --- |
| 商品型号 | Chromecast Voice Remote，G9N9N |
| 系统报告型号 | A0 |
| 厂商 | Google Inc. |
| VID / PID | `18D1:9450` |
| 固件 | `26.7` |
| macOS | 15.8.1，构建 24H32 |
| Voice Input Buddy | 26.10.26，构建 497 |
| ATVV 协商 | v1.0，16 kHz IMA ADPCM，音频帧大小 160 字节 |

问题表现为：语音键可以启动语音输入，而普通单键没有反应；刻意同时按下两个普通键时，应用有时能捕获操作；松开后没有释放报告，可能直到八秒缺失松开保护触发，映射动作才停止。

八秒保护只能避免按键无限保持，无法恢复准确的松开时间。旧版本的组合按键可能同时产生两个映射动作。

## 测试方法

先检查应用日志，确认输入监控及辅助功能权限已授予。随后退出 Voice Input Buddy，排除其独占连接、设备绑定、报告解析、按键映射和事件注入对测试的影响。独立程序以公开 IOHID 接口、非独占模式打开目标设备，同时记录原始报告和按键元素回调。

接着使用 Apple 官方 Additional Tools for Xcode 16.3 中的 PacketLogger，安装 Apple 签名的 Bluetooth Logging for macOS 描述文件并重启，确认实际出现 HCI／ACL 数据后再测试。PacketLogger 观察控制器接收的原始蓝牙通知，独立 IOHID 程序观察 macOS 是否向应用交付报告。

操作者确认完成两轮操作：

1. 单独短按上键三次，每次间隔约两秒，然后全部松开。
2. 按住返回，再加按上键形成双键，保持约两秒；只松开上键，继续保持返回约两秒；最后全部松开。

两轮均未按语音键。另一轮主动读取 input report 的公开接口实验每 200 ms 请求一次，读到的结果始终为空，未得到可用的替代按键状态。

## 原始报文与系统交付结果

HID 是普通按键使用的输入报告协议。这支设备的 report 1 描述符声明两个 8 位按键索引槽位，所以每条 GATT 按键通知应有 **2 字节按键数据**。macOS 向 IOHID 交付时再带上 report ID `01`，完整报告共 **3 字节**。GATT 通知和 IOHID 回调是否包含 report ID 必须区分，不能直接比较两层的总字节数。

以下时间为 2026-10-28 新加坡时间。通知来自同一连接和 ATT 属性；公开 IOHID 回调只在双键阶段出现。

| 操作 | 时间 | 实际 GATT 按键数据 | 数据长度 | IOHID 回调 |
| --- | --- | --- | --- | --- |
| 上键按下 1 | 14:27:23.410 | `03` | 1 字节 | 无 |
| 上键松开 1 | 14:27:23.678 | `00` | 1 字节 | 无 |
| 上键按下 2 | 14:27:25.017 | `03` | 1 字节 | 无 |
| 上键松开 2 | 14:27:25.266 | `00` | 1 字节 | 无 |
| 上键按下 3 | 14:27:27.042 | `03` | 1 字节 | 无 |
| 上键松开 3 | 14:27:27.324 | `00` | 1 字节 | 无 |
| 单独按住返回 | 14:30:09.232 | `0B` | 1 字节 | 无 |
| 再按上键形成双键 | 14:30:09.322 | `03 0B` | 2 字节 | **`01 03 0B`** |
| 只松开上键 | 14:30:12.190 | `00` | 1 字节 | 无 |
| 全部松开 | 14:30:15.081 | `00` | 1 字节 | 无 |

三次孤立上键均重复同一结果。双键原始通知与 IOHID 回调在同一毫秒出现，内容精确对应；这建立了蓝牙按键数据和应用接收报告的对应关系。本轮没有另行读取 GATT Report Reference 描述符。

脱敏 ATT 通知示例：

```text
上键按下：1B 46 00 03
全部松开：1B 46 00 00
上＋返回：1B 46 00 03 0B
```

`1B` 是通知类型，`46 00` 是属性 handle，后面的内容才是按键数据。HCI ACL 和 L2CAP 的长度字段均与实际数据相符，短包并非应用日志截断造成。上键按下本应发送 `03 00`，全部松开本应发送 `00 00`；实测缺少第二槽。

分步松开时还观察到：按照操作者确认的顺序，返回仍被按住，但通知已经是 `00`，未保留返回的 `0B`。这一附加状态问题只观察了一次，未单独复测，不用于概括所有组合操作。

## 故障原因和语音仍可用的原因

这次普通按键故障的原因是 **设备发送的按键报告与自己的描述符长度不一致，短报告没有进入 macOS 提供给应用的 HID 接收路径**。设备实际上发送了单键和松开信号，但应用收不到；双键恰好占满两个槽位，因此能够交付。

Apple 公开的 [IOHIDElementPrivate 源码](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDFamily/IOHIDElementPrivate.cpp) 对固定长度报告检查实际 bit 数是否小于描述符要求，这与实测现象吻合。本轮未对系统内部二进制函数插桩，因此不把具体丢弃点精确归于某个 DriverKit 方法。

语音键与音频使用独立的 **ATVV GATT 服务**，不依赖这些普通按键 HID 报告。因此，普通单键无法用于控制时，语音输入仍可正常工作。

`HIDBadBehavior` 系统标签及注册表里的 `IOHIDDevice Input Report Errors` 栏目不能单独证明根因。后者是预先建立的统计通道名称；本次结论依据的是原始通知、描述符以及同步 IOHID 回调的对照。

## 软件修复边界与使用说明

在当前公开接口路径下，应用无法给尚未收到的短报告补零。独立 CoreBluetooth 实验分别请求全部服务和 HID 服务 `1812`，都未获得 HID 服务；公开 HID 主动读取也没有得到按键状态。因此当前没有能恢复普通单键及松开报告的应用内修补路径。

真正恢复普通按键控制，需要设备按描述符发送完整槽位，并正确报告部分松开后的剩余按键状态，或者采用能够规范化报告的独立传输方案。增加权限、重新选择映射动作或缩短八秒保护时间，都没有解决已观察到的报告格式问题；双键 Enter 也只利用了恰好能收到的完整报告。

实验性功能：完成设置后，开启自定义按键映射，应用独占连接到 G9N9N 或已绑定为 Google 兼容设备、且使用相同索引报告描述符的设备时，同时按 **OK＋上／下／左／右任意一键**，应用将每条匹配的完整双键报告转换为一次 Enter，并且不执行这两个键的自定义映射。其他双键组合不触发普通按键映射，避免缺失松开时方向键持续连发。松开不会产生 Enter。设置向导的按键验证仍按原方式工作。

由于松开报告无法到达应用，无法判断两条相同报告是重复按下还是设备在持续按住时重复发送。此实现按收到的每条报告发送一次 Enter；连续按键及长按是否产生重复或遗漏、系统原生事件是否仍会出现，都需要真机验收。应用无法独占设备或映射关闭时，此实验功能不会发送 Enter。小米设备和使用其他报告格式的设备不走这段双键处理。兼容设备不保证都有相同固件缺陷，仍需各自测试。其他普通单键映射仍不受支持。

向导在最初按键验证、普通按键测试、重试及完成提示中说明上述双键方法与语音支持范围；原有通过条件、运行时映射开关、设备固件和系统 HID 驱动保持原样。
